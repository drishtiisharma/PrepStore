### 1. The Need for FastAPI and Problems Solved

FastAPI was created to address specific limitations in existing Python web frameworks regarding performance, development speed, and type safety.

*   **Performance Bottlenecks:** Traditional synchronous Python frameworks (like Flask or Django) handle one request at a time per worker process. FastAPI utilizes the ASGI (Asynchronous Server Gateway Interface) standard and Python’s `asyncio` library. This allows a single process to handle thousands of concurrent connections by switching tasks during I/O operations (database queries, API calls) rather than blocking execution. Benchmarks often place it comparable to Node.js and Go.
*   **Lack of Automatic Validation:** In older frameworks, developers manually parsed JSON bodies and validated fields, leading to repetitive boilerplate code and runtime errors. FastAPI integrates Pydantic directly into the routing layer. It automatically parses request data against defined Python types and returns standardized 422 Unprocessable Entity errors if validation fails.
*   **Documentation Drift:** API documentation often became outdated as code changed. FastAPI generates OpenAPI (formerly Swagger) schemas dynamically from function signatures and type hints at runtime. The documentation is always synchronized with the actual code implementation.
*   **Type Safety:** Python is dynamically typed, which makes large codebases difficult to maintain. FastAPI relies heavily on Python Type Hints (PEP 484). This enables static analysis tools (mypy, pylance) to catch errors before runtime and provides IDE autocompletion.

### 2. Core Terminologies

Understand these terms precisely for technical interviews:

*   **ASGI (Asynchronous Server Gateway Interface):** A specification for Python asynchronous web servers and applications. It replaces WSGI. ASGI supports HTTP, WebSockets, and background tasks. FastAPI is an ASGI framework; Uvicorn is an ASGI server that runs FastAPI.
*   **Pydantic:** A data validation library that uses Python type annotations. In FastAPI, Pydantic models define the structure, types, and constraints of request/response data. It performs parsing and validation at C-speed via Rust bindings in V2.
*   **Path Operation:** A combination of an HTTP method (GET, POST, etc.) and a URL path. In FastAPI, this is defined via decorators like `@app.get("/items")`.
*   **Dependency Injection (DI):** A design pattern where dependencies (database sessions, authentication logic, query parameters) are declared as function parameters. FastAPI has a built-in DI system (`Depends()`) that resolves these dependencies recursively before executing the path operation. This promotes modularity and testability.
*   **OpenAPI / Swagger UI:** OpenAPI is a language-agnostic specification for REST APIs. Swagger UI is a visualization tool that reads the OpenAPI JSON schema generated by FastAPI and renders an interactive testing interface.
*   **Request Body vs. Query Parameter vs. Path Parameter:**
    *   *Path Parameter:* Part of the URL structure (e.g., `/users/{user_id}`). Defined in the function signature matching the path variable name.
    *   *Query Parameter:* Appended to the URL after `?` (e.g., `?skip=0&limit=10`). Defined in the function signature as variables not present in the path.
    *   *Request Body:* JSON payload sent in POST/PUT/PATCH requests. Defined using a Pydantic model type hint.
*   **Response Model:** A Pydantic model specified in the decorator (`response_model=UserOut`). It filters output data, ensuring sensitive fields (like passwords) are excluded and response structure is guaranteed regardless of what the function returns.

### 3. Key Technical Concepts for Interviews

#### Asynchronous Programming (`async` / `await`)
*   **Definition:** Cooperative multitasking within a single thread.
*   **Mechanism:** When an `await` expression is encountered, control yields back to the event loop, allowing other coroutines to run while waiting for I/O.
*   **Interview Point:** Know when to use `def` vs `async def`. Use `async def` for I/O-bound operations (DB, HTTP). Use regular `def` for CPU-bound tasks; FastAPI runs sync functions in a thread pool to prevent blocking the event loop. Mixing them incorrectly causes performance degradation.

#### Dependency Injection System
*   **Functionality:** Dependencies can be nested. A dependency can depend on another dependency. FastAPI caches dependency results per request by default (`use_cache=True`) to avoid redundant DB calls or computations.
*   **Use Cases:** Authentication verification, pagination parameter extraction, database session management, role-based access control.
*   **Testing Benefit:** Dependencies can be overridden using `app.dependency_overrides` during testing, allowing you to mock databases or auth systems without modifying application code.

#### Data Validation Flow
1.  Request arrives.
2.  FastAPI matches route.
3.  Path/Query params are extracted and coerced to declared types.
4.  If body exists, raw bytes are decoded to JSON.
5.  Pydantic validates all inputs against declared models.
6.  If invalid → Automatic 422 response with detailed error location.
7.  If valid → Validated Python objects passed to handler.

# REST API 

REST (Representational State Transfer) is an architectural style for designing networked applications. It defines a set of constraints that, when applied to an API, ensure scalability, simplicity, and interoperability.

### 1. Core Constraints of REST

To be considered truly RESTful, an API must adhere to these principles:

*   **Client-Server Separation:** The user interface concerns (client) are separated from data storage concerns (server). This allows each to evolve independently.
*   **Statelessness:** Each request from the client to the server must contain all the information necessary to understand and process the request. The server does not store any client context between requests. Session state is held entirely on the client.
*   **Cacheability:** Responses must define themselves as cacheable or not. This prevents clients from reusing stale or inappropriate data after subsequent requests.
*   **Uniform Interface:** A standardized way of interacting with resources. This includes:
    *   *Resource Identification:* Resources are identified in requests using URIs (Uniform Resource Identifiers).
    *   *Resource Manipulation through Representations:* Clients hold representations of resources (e.g., JSON) and include enough information to modify or delete the resource on the server.
    *   *Self-descriptive Messages:* Each message includes enough information to describe how to process it (e.g., MIME types like `application/json`).
    *   *Hypermedia as the Engine of Application State (HATEOAS):* Ideally, responses contain links to related actions, allowing the client to navigate the API dynamically.
*   **Layered System:** The architecture can be composed of hierarchical layers. A client cannot ordinarily tell whether it is connected directly to the end server or an intermediary (like a load balancer or security gateway).

### 2. HTTP Methods and Their Semantic Meaning

REST relies on standard HTTP methods to perform operations on resources. Using the correct method is critical for interview discussions regarding idempotency and safety.

| Method | Action | Idempotent? | Safe? | Description |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | Retrieve | Yes | Yes | Fetches a representation of a resource. Should not alter server state. |
| **POST** | Create | No | No | Submits data to be processed. Often creates a new subordinate resource. |
| **PUT** | Update/Replace | Yes | No | Replaces the entire target resource with the request payload. |
| **PATCH** | Partial Update | No* | No | Applies partial modifications to a resource. |
| **DELETE** | Remove | Yes | No | Removes the specified resource. |

*   **Idempotency:** An operation is idempotent if making multiple identical requests has the same effect as making a single request. GET, PUT, and DELETE are idempotent. POST is not (sending a "create order" request twice might create two orders).
*   **Safety:** A safe method does not change the state of the server. Only GET is considered safe.

### 3. Resource Naming and Status Codes

*   **Nouns, not Verbs:** URIs should represent resources (nouns), not actions (verbs).
    *   *Correct:* `GET /users/123`
    *   *Incorrect:* `GET /getUsers/123`
*   **Pluralization:** Use plural nouns for collections.
    *   *Collection:* `/users`
    *   *Single Item:* `/users/123`
*   **Standard Status Codes:**
    *   **2xx (Success):** 200 OK, 201 Created, 204 No Content.
    *   **3xx (Redirection):** 301 Moved Permanently.
    *   **4xx (Client Error):** 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity (common in FastAPI/Pydantic).
    *   **5xx (Server Error):** 500 Internal Server Error, 503 Service Unavailable.

### 4. How FastAPI Implements REST

FastAPI is designed to build RESTful APIs efficiently by mapping Python functions directly to these REST concepts:

1.  **Path Operations map to HTTP Methods:** The decorators (`@app.get`, `@app.post`) enforce the uniform interface constraint by explicitly defining which HTTP method triggers which logic.
2.  **Pydantic Models handle Representations:** They define the structure of the JSON representations sent between client and server, ensuring self-descriptive messages via the generated OpenAPI schema.
3.  **Dependency Injection manages Statelessness:** By injecting dependencies like database sessions or auth tokens into each request handler, FastAPI ensures that every request has the necessary context without relying on server-side session memory.

### Interview Preparation: REST-Specific Questions

1.  **"What is the difference between PUT and PATCH?"**
    *   *Answer:* PUT replaces the entire resource. If you send a PUT request with only one field, the other fields may be nullified. PATCH applies only the changes provided in the payload.
2.  **"Why is statelessness important in REST?"**
    *   *Answer:* It improves scalability. Because the server doesn't need to remember previous interactions, any server in a cluster can handle any request. It also simplifies caching and load balancing.
3.  **"How do you handle versioning in a REST API?"**
    *   *Answer:* Common strategies include URI versioning (`/v1/users`), Header versioning (`Accept: application/vnd.myapi.v1+json`), or Query parameter versioning (`?version=1`). URI versioning is the most explicit and widely used.
4.  **"Explain HATEOAS."**
    *   *Answer:* It means the API response should provide links to related resources. For example, a response for a "User" might include a link to that user's "Orders." This reduces coupling between client and server logic.
